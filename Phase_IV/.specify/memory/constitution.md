# 📜 Constitution.md
## Project: Evolution of Todo
## Phase II – Full-Stack Multi-User Web Application

---

## 1. Purpose & Vision
This project evolves the Todo application from a **single-user, in-memory CLI tool** into a **secure, multi-user, full-stack web application** with persistent storage and authentication.

The system reflects **real-world software evolution**:
- **Spec-driven development:** Design before implementation.
- **Security-first:** Identity is core to the data model.
- **Clean separation:** Next.js (Frontend) and FastAPI (Backend).
- **Tooling:** All features must be implemented **exclusively using Claude Code and Spec-Kit Plus**. Manual coding is strictly prohibited.

---

## 2. Spec-Driven Development (MANDATORY)
- Every feature must begin with a **written specification**.
- No implementation may occur without a completed feature spec, validated checklist, and approved plan.
- Code may only be generated by **Claude Code**.
- Specs must be refined until correct behavior is produced.

---

## 3. Architectural Principles
### 3.1 Separation of Concerns
- **Frontend:** Next.js App Router. User interface and identity issuance.
- **Backend:** FastAPI. Business logic, API layer, and authorization enforcement.
- **Database:** Neon Serverless PostgreSQL (SQLModel ORM).
- **Authentication:** JWT-based identity verification.

---

## 4. Frontend Rules (Next.js)
- Responsible for User Signup, Signin, and Session Management.
- **Identity Provider:** Uses Better Auth to issue JWT tokens.
- **Communication:** Must attach a valid JWT token to every API request header.
- **Logic:** Must not enforce authorization; the Backend remains the source of truth.

---

## 5. Backend Rules (FastAPI)
- **Statelessness:** The backend must not store session state.
- **Verification:** Must verify JWT signatures for every protected route.
- **Identity:** Extract authenticated user identity from the JWT.
- **Status Codes:** Must strictly use:
  - `401 Unauthorized` (Missing/Invalid Token)
  - `403 Forbidden` (User attempting to access another user's data)
  - `404 Not Found` (Resource does not exist)

---

## 6. Authentication Rules (JWT)
- **Secret Management:** A shared secret (`BETTER_AUTH_SECRET`) must be used for signing (Frontend) and verifying (Backend).
- No session-based cookies or server-side session lookups in the backend.

---

## 7. Data & Persistence Rules
- **Storage:** All data stored in **Neon Serverless PostgreSQL**.
- **ORM:** Must use **SQLModel**.
- **Ownership:** Every task record must contain a `user_id` foreign key.
- **Isolation:** Users may **only** access or modify tasks where `task.user_id == authenticated_user_id`.

---

## 8. API Design Rules
- APIs must be RESTful.
- **Pattern:** `/api/tasks` or `/api/tasks/{task_id}`.
- **Authorization:** Even if a `user_id` is passed in a path or body, the Backend **must** validate it against the ID extracted from the JWT.

---

## 9. Security Principles
- All endpoints require authentication by default.
- No anonymous access to task data.
- **Robustness:** Backend must remain secure even if the Frontend is compromised.

---

## 10. Testing & Validation
- Every feature must include **Unit tests** and **API-level integration tests**.
- Authentication and "Cross-User Data Access" (security) failure cases must be explicitly tested.

---

## 11. Tooling Rules
- **Claude Code** is the sole implementation agent.
- **Spec-Kit Plus** governs the lifecycle: Specification → Planning → Implementation.
- Manual code changes are forbidden.

---

## 12. Definition of Done (Phase II)
A feature is complete only when:
1. Specification is approved.
2. Code is generated via Claude Code.
3. Tests (including security/auth tests) pass.
4. User data isolation is verified.

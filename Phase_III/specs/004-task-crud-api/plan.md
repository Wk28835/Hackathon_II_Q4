## Summary

Implement a secure, multi-user Task CRUD API backend using FastAPI and SQLModel. The API provides RESTful endpoints for authenticated users to manage their tasks with JWT-based authentication, automatic user data isolation, and persistent PostgreSQL storage. All endpoints require valid JWT tokens, enforce user ownership validation, and return appropriate HTTP status codes (401/403/404) for security and authorization failures.

## Design Decisions

### 1. Authentication & Authorization Strategy

**Decision**: JWT-based stateless authentication with signature verification

**Rationale**:
- Phase II Constitution mandates stateless backend (no session storage)
- JWT token issued by Frontend (Better Auth) with shared secret
- Backend extracts user_id from token payload
- Every protected endpoint verifies JWT signature without database lookup

**Implementation**:
- FastAPI dependency injection for JWT verification
- Pydantic model for token claims (`TokenPayload` with `sub` = user_id)
- python-jose library for signature verification
- 401 Unauthorized for missing/invalid tokens
- Automatic user_id extraction for data isolation

### 2. User Data Isolation

**Decision**: Mandatory `user_id` filtering on all read/write operations

**Rationale**:
- Constitution principle: "Users may **only** access or modify tasks where `task.user_id == authenticated_user_id`"
- Prevents cross-user data leakage
- Must be enforced in database queries, not just response filtering

**Implementation**:
- Task model includes `user_id` foreign key (non-nullable)
- All queries filter: `where Task.user_id == current_user_id`
- Update/delete operations validate ownership before modification
- 403 Forbidden returned for ownership violations (not 404, to avoid info leakage per spec)

### 3. API Response Format & Status Codes

**Decision**: RESTful JSON responses with strict HTTP status codes

**Rationale**:
- RESTful patterns align with Phase II API design rules
- Explicit status codes (401/403/404) provide clear error semantics
- JSON responses include task objects for create/update operations

**Implementation**:
- POST /api/tasks → 201 Created (or 200 OK per spec)
- GET /api/tasks → 200 OK
- GET /api/tasks/{id} → 200 OK or 404 Not Found
- PUT /api/tasks/{id} → 200 OK or 400/403/404
- DELETE /api/tasks/{id} → 204 No Content or 400/403/404
- Error responses: `{"detail": "error message"}`

### 4. Database Schema

**Decision**: SQLModel ORM with PostgreSQL

**Rationale**:
- SQLModel provides both ORM capabilities and Pydantic validation
- PostgreSQL supports ACID transactions and foreign key constraints
- Neon Serverless PostgreSQL is Phase II standard
- SQLAlchemy Core integration for advanced queries if needed

**Implementation**:
- Task table: id (UUID/int PK), user_id (FK to users), title, description, status, created_at, updated_at
- User table: id (UUID/int PK), email, ... (managed by Frontend/Better Auth)
- Cascade delete optional (consider data retention policies)
- Timestamps auto-managed by database defaults

### 5. Validation Strategy

**Decision**: Multi-layer validation (Pydantic schemas + database constraints)

**Rationale**:
- Spec requires title non-empty validation
- Prevents invalid states at API boundary
- Database constraints provide defense-in-depth

**Implementation**:
- Pydantic `TaskCreate` schema with `title` required, non-empty
- Pydantic `TaskUpdate` schema with optional title/description, title non-empty if provided
- Database NOT NULL constraint on title and user_id
- SQLModel field constraints: `title: str = Field(..., min_length=1)`

### 6. Testing Strategy

**Decision**: Unit + Integration + Security-focused tests

**Rationale**:
- Spec requires "Authentication and Cross-User Data Access failure cases must be explicitly tested"
- Need coverage for all CRUD operations + edge cases
- Security tests critical: JWT validation, 403 response verification

**Implementation**:
- `tests/unit/`: Model and schema validation tests
- `tests/integration/`: API endpoint tests with real database
- `tests/security/`: JWT failures, cross-user access attempts, 403 responses
- pytest fixtures: test database, test user tokens, sample tasks
- Coverage target: >90% on critical paths
